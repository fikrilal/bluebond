## BlueBond v0.1.1

Patch release for BlueZ store permission diagnostics.

## Install

```bash
curl -LO https://github.com/fikrilal/bluebond/releases/download/v0.1.1/bluebond-0.1.1-x86_64-unknown-linux-gnu.tar.gz
curl -LO https://github.com/fikrilal/bluebond/releases/download/v0.1.1/bluebond-0.1.1-x86_64-unknown-linux-gnu.tar.gz.sha256
sha256sum -c bluebond-0.1.1-x86_64-unknown-linux-gnu.tar.gz.sha256
tar -xzf bluebond-0.1.1-x86_64-unknown-linux-gnu.tar.gz
sudo install -m 0755 bluebond-0.1.1-x86_64-unknown-linux-gnu/bluebond /usr/local/bin/bluebond
```

## Fixed

- `scan` now reports an actionable BlueZ store permission error when `/var/lib/bluetooth` is not readable by the current user.
- `doctor` now checks whether `/var/lib/bluetooth` is readable, not only whether it exists.
- Docs now clarify that read-only commands do not mutate state but may still need `sudo` to read protected BlueZ bond records.

## Why This Matters

Many Linux distributions store BlueZ bond records under:

```text
/var/lib/bluetooth
```

with permissions like:

```text
drwx------ root root
```

In that setup, commands such as `scan`, `plan`, and `apply --dry-run` are still read-only, but they need root permission to inspect the real bond records:

```bash
sudo bluebond scan --windows-root /mnt/windows
sudo bluebond plan --windows-root /mnt/windows
sudo bluebond apply --dry-run --windows-root /mnt/windows
```
